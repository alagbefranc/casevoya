### ORG-06a: offboarding hands over leads and booking hosting (migration)

What exists:

- `public.staff_offboarding_preview(org, membership)` and `public.offboard_staff_member(org, membership, receiver)` in `supabase/migrations/20261019217000_settings_staff_admin.sql` (around lines 312–640).
  - They move open internal tasks (and their deadlines), case-manager and assistant parties, on-hold ownership, and consultant-of-record matters (only to a verified licence). For each moved matter they create a "Review client authority" task.
  - They then disconnect the person's connections, revoke their memberships and sessions, and audit `membership.offboarded`.
  - Everything goes to **one** receiver.
- App side:
  - `src/modules/settings/settings-staff-admin-actions.ts` (`offboardStaff`, preview);
  - `src/modules/sheet/settings-staff-admin-present.ts`;
  - the Team tab dialog.
- Data still left behind:
  - `public.leads.owner_membership_id` (`20261019201100_leads_core.sql`). Open leads are those whose stage `kind = 'open'` (enum `lead_stage_kind`: open, converted, lost, archived).
  - `public.booking_event_type_hosts (event_type_id, membership_id, position)`, unique per `(event_type_id, membership_id)`.
  - `public.bookings` columns `host_membership_id`, `host_user_id`, `host_name` and `host_time_zone`. Live statuses are `held`, `pending_payment` and `confirmed`. The exclusion constraint `bookings_no_double_booking` (on host_user_id plus the blocked range) means moving a booking to a busy host fails. Catch that and name the booking in the error.
  - `public.booking_events` is the append-only history. Its `kind` check allows only held, confirmed, rescheduled, cancelled, expired, no_show and completed. Changing hosts needs either a new kind (this alters a check constraint, so it needs a migration) or an audit-only record.

Proposed design:

1. **Preview.** Redefine `staff_offboarding_preview` to also return:
   - `leads`: id and display label, for open leads they own;
   - `booking_types`: id and title, for types they host, with whether any other active host remains;
   - `bookings`: id, title, `starts_at` and type, for upcoming live bookings they host.
   - As in the existing preview, give labels only and never client contact details.
2. **Offboard.** Add `offboard_staff_member(org, membership, receiver, p_handover jsonb)`, where `p_handover` is
   `{ "leads": {lead_id: membership_id}, "booking_types": {type_id: membership_id}, "bookings": {booking_id: membership_id} }`.
   - Every listed item must have a choice; refuse with a clear message otherwise.
   - Each choice must be an active staff member who isn't the leaver.
   - For booking types and bookings, the chosen host must be able to host. Mirror the checks the scheduling code uses for hosts.
   - Then:
     - move each lead's owner;
     - replace the host row (delete it if the new host already hosts that type);
     - move each booking's host fields and bump `ics_sequence`;
     - write audit events (`lead.owner_reassigned`, `booking_type.host_reassigned`, `booking.host_reassigned`), each with `reason: 'offboarding'`.
   - Then run the existing steps unchanged.
3. **Old 3-argument function.** Redefine `offboard_staff_member(org, membership, receiver)` to call the new one with `'{}'`. It will then refuse whenever the leaver still owns leads or hosts bookings. This closes the bypass.
4. **UI.** In the Team tab offboard dialog, add a section for each list with one "New owner" or "New host" select per row, defaulting to the main receiver. Save stays disabled until every row has a choice.
5. **Undecided.** Whether the attendee of a moved booking is emailed about the new host isn't decided; it overlaps ORG-06b. If it isn't built, say so in the PR.
6. **Tests.** PGlite RLS tests modelled on the existing offboarding tests (grep `offboard_staff_member` in `tests/`), plus a presenter test. The spec's UI test is step 1 of ORG-06.
